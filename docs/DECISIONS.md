## D-01 — Mirror Prosper's stack (2026-09-24, planning)
Context: Assignment for a team running FastAPI + PostgreSQL + React/TS.
Decision: FastAPI, PostgreSQL, React + TypeScript.
Alternatives: Django, Next.js full-stack. Rejected: less relevant to the role.
Consequences: React is new to the author; see `docs/react-for-angular-devs.md`.

## D-02 — Single process, in-process scheduler (2026-09-24, planning)
Context: 10–15 hours of build time; one user base, low volume.
Decision: API, APScheduler and pipeline in one FastAPI process; audio on local disk.
Alternatives: Celery/RQ + Redis workers; Exa Monitors for scheduled search (needs a public webhook).
Consequences: Jobs would double-run with two instances. Fix path: DB advisory lock or a queue + worker.

## D-03 — Two-host dialogue, English, tunable length (2026-09-24, planning)
Context: Episode quality is the main judged output.
Decision: Two hosts (Alex anchor, Sam co-host), English, 3–12 minutes (default 6), user-tunable.
Alternatives: Solo narrator (simpler, less engaging).
Consequences: More prompt and voice-tuning work; chunking must respect turn and story boundaries.

## D-04 — ElevenLabs Text to Dialogue on eleven_v3, chunked at story boundaries (2026-09-24, planning)
Context: ElevenLabs recommends ≤ 2,000 characters per dialogue request; v3 has no request stitching.
Decision: Pack whole script sections into ≤ ~1,800-char chunks; one request per chunk; fixed seed; concatenate with ffmpeg and loudness-normalize to −16 LUFS.
Alternatives: One call per episode (too large); one call per line (loses turn-taking prosody); GenFM Create Podcast API (black box over script, grounding and personalization).
Consequences: Chunk boundaries are the main audio risk; they land on topic changes where a pause is natural.

## D-05 — OpenAI GPT-6 family, split by task (2026-09-24, planning)
Context: Different steps need different cost/quality.
Decision: Luna (reasoning none) for query planning, classification and grounding checks; Sol (reasoning medium) for profile extraction and scripting; Astra only as a quality ceiling experiment for `sample.mp3`.
Alternatives: One model for everything.
Consequences: TTS (~$0.60/episode) dominates cost; LLM steps are ~$0.10. Savings come from shorter TTS input, not cheaper LLMs. Model IDs to be confirmed in phase 00.

## D-06 — Exa as the only v1 news source (2026-09-24, planning)
Context: Brief requires news via APIs or scraping; users can type any interest.
Decision: Exa `/search` driven by LLM-planned queries; curated RSS for a niche is a later step. Hacker News, Reddit and X dropped.
Alternatives: NewsAPI.org (dev-only free plan, no full text, ~24h delay), other aggregators (snippet-only free tiers), Reddit (2–4 week approval queue), X (pay per read, low signal).
Consequences: Coverage depends on Exa's index; very fresh or niche pages may be missed.

## D-07 — Exa request shape follows Exa's official guidance (2026-09-24, planning)
Context: Exa's `build-with-exa` skill documents over-specification as the most common mistake.
Decision: `/search` with `query`, `type: "auto"`, `contents.highlights: true` and `startPublishedDate` for the episode window (a stated window we must enforce). No `category`, `numResults`, domain filters or `maxAgeHours`. Retry once without the date filter if a query returns < 3 results. Full text only for selected URLs via `/contents` (`text: true`), checking per-URL `statuses`.
Alternatives: `category: "news"` (Exa advises against inferring categories); full text for every result (pays for text we never use).
Consequences: Classification runs on highlights, scripting on full text. Exa's `costDollars` gives exact search cost.

## D-08 — Interest profile via guided interview + per-episode focus request (2026-09-24, planning)
Context: Search needs concrete queries; users describe interests loosely.
Decision: LLM extracts an editable structured profile once; each episode an LLM plans queries from the profile, an optional focus request and recent headlines.
Alternatives: Plain topic tags (weak queries); full chat interview (time-expensive).
Consequences: Planned queries are stored on the episode, so every selection is traceable.

## D-10 — `scripts/setup.py` as the single environment-bootstrap entry point (2026-09-24, phase 00)
Context: Phase 00 needed `uv` and Exa's `build-with-exa` skill, and neither `uv` nor `node`/`npx` were preinstalled on this machine; both had to be worked around by hand (`pip install uv`, `git clone` the skill repo instead of `npx skills add`). That workaround needs to be reproducible for anyone re-cloning the repo, not rediscovered by hand every time.
Decision: `scripts/setup.py`, a dependency-free Python script (Python is guaranteed present; `uv` and `node` are not), is the one command that gets a fresh clone to a working state: installs `uv` via `pip install uv` if missing, copies `.env.example` → `.env` if missing (never overwrites), runs `uv sync` in `backend/`, and installs the `build-with-exa` skill via `npx` if available or a `git clone` fallback (with a Windows-safe recursive delete, since `shutil.rmtree` chokes on git's read-only pack files) if not. `CLAUDE.md` now documents `uv add <package>` (never hand-editing `pyproject.toml` or bare `pip install`) as the only way to add a backend dependency, followed by re-running `scripts/setup.py`/`uv sync` and committing the updated `pyproject.toml` + `uv.lock` alongside the code that needs it.
Alternatives: A `setup.sh`/`setup.ps1` pair — rejected, this project's dev machine mixes Git Bash and PowerShell and a single Python script runs identically in both with no syntax duplication. A bare `README` instruction to run `uv sync` — rejected, it doesn't cover the "`uv`/`node` isn't installed yet" case this session actually hit.
Consequences: `scripts/setup.py` must be kept in sync by hand whenever a future phase needs a new external tool (the way `build-with-exa` was needed in phase 00) — there is no test enforcing that, only the `CLAUDE.md` rule.

## D-11 — One venv only (`backend/.venv`); fix the run command, not a second venv (2026-09-24, phase 00)
Context: Running a `scripts/smoke/*.py` script the "obvious" way — bare `python scripts/smoke/openai_check.py`, or even `uv run python scripts/smoke/openai_check.py` from the repo root — reproducibly hits `ModuleNotFoundError: No module named 'openai'`. Both silently fall back to the system Python (there's no `pyproject.toml` at the repo root for `uv run` to anchor on), not `backend/.venv`, even though `scripts/setup.py` had already `uv sync`'d `backend/.venv` correctly. The user asked whether `scripts/setup.py` should create a second `.venv` (root or `scripts/`) to fix this.
Decision: No second venv. `uv run --project backend python scripts/<path>.py`, run from the repo root, uses the existing `backend/.venv` correctly with no `cd` needed — verified live against `openai_check.py`. Fixed the documented invocation everywhere instead: `scripts/setup.py`'s printed hint, the `Run:` line in each `scripts/smoke/*.py` docstring, and added both a `CLAUDE.md` Commands entry and an Environment-setup rule spelling out that non-`backend/` scripts need `--project backend` or they'll silently use the wrong interpreter.
Alternatives: A second venv under `scripts/` (the user's suggestion) with its own dependency manifest — rejected: it would duplicate openai/exa-py/elevenlabs/python-dotenv across two lockfiles that drift the moment `backend/pyproject.toml` changes, directly contradicting D-10's "single dependency source of truth" rule from earlier this same phase.
Consequences: every future non-`backend/` script (e.g. `eval/` scripts in phase 04) must be invoked with `uv run --project backend ...` from the repo root, or documented with an equivalent explicit `cd backend &&` — bare `python`/bare `uv run` from outside `backend/` is a known foot-gun now written down in `CLAUDE.md`.

## D-12 — ElevenLabs per-call cost comes from the `character-cost` response header (2026-09-24, phase 00)
Context: `text_to_dialogue.convert()`'s response body is the audio itself, so the normal SDK return value has nowhere for a cost number to live, and D-09 already found this project's key can't read `user.subscription.get()` (no account-level quota either). Needed a real number for `Usage.units_in`/`pipeline_steps.cost_usd` in the future TTS adapter (phase 03) that isn't just re-deriving `len(text)`.
Decision: confirmed live via `client.text_to_dialogue.with_raw_response.convert(...)` (a `@contextlib.contextmanager`-decorated method on `elevenlabs` SDK 2.69.0, so `with ... as resp:` is required) — a 36-character 2-turn test call (`scripts/smoke/elevenlabs_headers.py`) returned response header `character-cost: 36`, exactly matching characters sent including tags, plus `request-id: OgDy9eSGGYSpJ3Lnmh9p` and a bonus `tts-latency-ms: 605`. The TTS adapter will read `Usage.units_in` from `character-cost` (tagged `usage_source="header"` on `pipeline_steps`) and store `request-id` on the row for debugging, with a character-count fallback (`usage_source="estimated"`) only if the header is ever absent. `.claude/skills/elevenlabs-dialogue/SKILL.md` updated: the documented adapter call now uses `with_raw_response`, not plain `.convert()`.
Alternatives: estimating `Usage.units_in` purely from `sum(len(t.text) for t in turns)` — rejected as the default (kept only as a defensive fallback) now that the provider's own billed number is directly readable and confirmed present on every phase 00 call.
Consequences: summing `character-cost` across `pipeline_steps` rows is this project's only available "characters used so far" figure (no account-level quota to check it against, per D-09) — `pricing.py`'s dollar-per-character rate stays an estimate, called out as such in `solution.md`, since the real plan pricing isn't visible with this scoped key. `history-item-id` came back `not_stored` on this call, so ElevenLabs-side history/playback isn't available as a fallback audit trail either — `pipeline_steps` is the only record. Dashboard shows characters as exact, dollars as estimated.

## D-17 — Native enum columns store `.value`, not SQLAlchemy's default `.name` (2026-09-24, phase 01)
Context: SQLAlchemy's `Enum(SomePyEnum)` persists each member's `.name` (e.g. `"PENDING"`) by default, not `.value` (`"pending"`) — true even for an `enum.StrEnum` member that *is* a string. ARCHITECTURE §5/§7 specify lowercase enum values, and `pipeline_steps.stage` (a plain string column) already stores lowercase (`EpisodeStatus.PLANNING.value`), so the enum columns would otherwise be silently inconsistent with both the docs and the sibling column.
Decision: added a `_pg_enum(enum_cls, name)` helper in `app/models.py` that passes `values_callable=lambda members: [m.value for m in members]` to every native enum column (`episode_status`, `episode_trigger`, `content_source`, `step_status`).
Alternatives: SQLAlchemy's default `.name`-based storage — rejected as contradicting the documented lowercase values and surprising anyone querying the DB directly.
Consequences: caught before the first migration was ever applied, by inspecting the autogenerated migration's `sa.Enum(...)` calls (they showed uppercase names) rather than assuming the default was correct — the same check is worth repeating for any enum column added in a later phase.

## D-18 — Test DB isolation, and a SQLAlchemy URL-masking footgun (2026-09-24, phase 01)
Context: tests need a real Postgres (JSONB and native enums aren't SQLite-portable) but must never touch the developer's real dev database. While wiring this up, `backend/tests/conftest.py` derived the test DB's connection string with `str(url.set(database=f"{name}_test"))` — which compiled and looked correct when printed, but every test then failed with `password authentication failed for user "podcast"` even though the same credentials worked fine everywhere else.
Decision: the cause is that `str(sqlalchemy.engine.URL)` masks the password as the literal text `"***"` by default (it exists for safe logging) — so the "working" connection string actually had `***` baked in as the real password. Fixed by using `url.render_as_string(hide_password=False)` instead of `str(url)` when building a connection string that will actually be used to connect. `conftest.py` now creates a `<dbname>_test` database via a maintenance connection if missing, and calls `Base.metadata.create_all()` against it once per session — not `alembic upgrade head`, to keep tests fast and decoupled from migration authoring (whose own correctness is covered separately by the `docker compose up -d db && alembic upgrade head` acceptance check).
Alternatives: SQLite for tests — rejected, per CLAUDE.md's Postgres-only stack and this schema's use of JSONB/native enums. Debugging by re-checking credentials first — the confusing part was that the error pointed at Postgres auth, not at Python string handling, so this is written down for the next person who hits the same red herring.
Consequences: any future code that builds a Postgres connection string from a `sqlalchemy.engine.URL` object must use `render_as_string(hide_password=False)`, never `str()`, for anything other than logging.

## D-19 — `bcrypt` pinned below 4.1 for `passlib` compatibility (2026-09-24, phase 01)
Context: `passlib[bcrypt]` 1.7.4 probes `bcrypt.__about__.__version__` to detect its backend version; `bcrypt>=4.1` removed that attribute. The failure mode is misleading: every `CryptContext.hash()` call (i.e. every `seed-users` run) raised `ValueError: password cannot be longer than 72 bytes, truncate manually if necessary`, even for the 5-character seed passwords — a known passlib/bcrypt incompatibility, not a real length violation. This was flagged as a risk during planning and hit live on the first `seed-users` test run.
Decision: pinned `bcrypt<4.1` alongside `passlib[bcrypt]` via `uv add "bcrypt<4.1"` (resolved to 4.0.1).
Alternatives: switching to a different hashing library — rejected, this is a narrow, well-understood incompatibility with a one-line fix, not a reason to change libraries.
Consequences: revisit this pin if `passlib` ships a fix for the `bcrypt>=4.1` probe, or if `bcrypt`/`passlib` are ever upgraded independently of each other.

## D-21 — Fetch stage: retry-without-date-filter rarely fires; article_scores keyed by (article, topic) (2026-09-24, phase 02)
Context: phase 02's acceptance run (demo user: health tech + AI voice agents for work, Formula 1 for fun, celebrity gossip avoided, focus request "the latest on prior authorization rules") planned 11 queries (2 per topic across 4 extracted topics, 3 for the focus request) and fetched all of them concurrently (4 workers) against real Exa.
Decision / findings: every one of the 11 date-filtered `/search` calls returned well over the 3-result retry threshold (90 unique articles total after URL-normalized dedupe, 8-20 per topic), so the retry-without-`startPublishedDate` path documented in D-09/the exa-news-search skill did not fire even once on this real run — consistent with D-09's phase 00 finding that the date filter rarely changes result counts for active topics; it only matters for slow-moving or narrow queries, exercised here only by a synthetic stub double in `test_fetch.py` since `FakeSearchSource`'s fixture can't reproduce a real <3-result response. Separately, `article_scores` is keyed `(episode_id, article_id, topic)`, not `(episode_id, article_id)`: since relevance is scored per topic (ARCHITECTURE §5.3) and the same article can legitimately match more than one of a user's topics, one row per matching topic is correct, and fetch's own within-run dedupe uses that same composite key so two queries sharing a topic don't double-insert.
Alternatives: deduping `article_scores` on `article_id` alone — rejected, it would silently drop an article's second topic match, which ranking (phase 03) needs to score separately.
Consequences: real cost for the acceptance run: profile extraction $0.0047 (gpt-6-sol), planning $0.0002 (gpt-6-luna, 11 queries planned in one call), fetching $0.0770 (Exa, 11 queries × search + zero retries) — about $0.082 total, well under the $5 daily cap. `article_scores` will need a unique constraint on `(episode_id, article_id, topic)` if phase 03's ranking stage does its own upserts against it; not added here since phase 02 only inserts, never updates, that table.

## D-22 — Known gap: same-event collapsing is unbuilt, unscored candidates can duplicate a story (2026-09-24, phase 02)
Context: fetch's URL-hash dedupe (D-21) only catches the same article at the same URL; it cannot catch two different outlets independently covering the same event (e.g. two articles "F1 winner is X" from different sites). `docs/phases/03-pipeline.md` already lists same-event collapsing under its own "Cut first" line, meaning the documented fallback for phase 03 is a simple top-N-per-topic selection with no event-awareness. Walked through the consequence during phase 02 review: with collapsing skipped, both same-event articles can independently score highly under one topic, both get selected as separate `story` sections (each `source_ids` of length 1), and the episode literally repeats the same news beat twice — a real, audible defect in `sample.mp3`, the primary judged artifact. Checked the `podcast-script` skill for a safety net: it has no rule telling the script writer to detect or merge duplicate-event stories, so nothing catches this after selection either.
Decision: accept the gap for now — ship phase 03 with simple top-N-per-topic selection (no same-event collapsing), consistent with its own documented cut. Record it here explicitly as a known issue rather than letting it be silently re-discovered later, and defer a real fix to a future phase once the full pipeline (plan → fetch → rank → extract → script → voice → assemble) is working end to end — tentatively phase 09 (stretch), not yet added as a formal phase 09 item since it isn't guaranteed to make the cut.
Alternatives considered: (a) relying on the script writer to notice duplicate events on its own and merge them — rejected as unsafe for the flagship deliverable, since nothing in the current prompt design asks it to and prompt-following isn't a substitute for a structural fix; (b) building a full same-event classifier pass now — rejected as scope creep before the pipeline even produces one working episode end to end, exactly why phase 03 lists it as its own first thing to cut.
Consequences: the schema and architecture already anticipate the eventual fix and require no redesign — `ArticleScore.same_event_as_url` exists, and ARCHITECTURE §5.5's own example JSON already shows one `story` section's `source_ids` citing two article ids (`["a12", "a15"]`), and `docs/phases/03-pipeline.md`'s extract step already says to fetch "selected URLs (+ their extra sources, max 2 per story)" — so the intended mechanism is: collapse a same-event loser into its winner's `same_event_as_url`, extract both, and let one story section cite both as sources (multi-outlet attribution), not skip the loser or give it its own section. When this is revisited, the cheapest real fix is likely a pre-selection heuristic (title/entity overlap + same-day publish date within one topic, keep the top-scored one) rather than an LLM judgment call, since the current `Classifier.score()` protocol scores one article in isolation with no visibility into sibling candidates to compare against.

## D-23 — Classifier protocol takes an explicit topic parameter (2026-09-24, phase 03)
Context: fetch (phase 02) already tags each `article_scores` row with the one topic that found it — one row per (article, topic) match (D-21) — because relevance genuinely differs per topic. ARCHITECTURE §6's literal `Classifier.score(article, profile, recent_headlines)` signature has no way to tell the classifier which of the profile's several topics to score against; it can only re-guess one itself.

## D-25 — Selection formula, chunker, and script validation thresholds (2026-09-24, phase 03)
Decision: implemented as ARCHITECTURE §5.3/§5.5 and the elevenlabs-dialogue skill specify: final = relevance × newsworthy × recency-decay (half-life 3 days; undated or future-dated articles get decay=1.0, since fetch already drops out-of-window undated results, so "undated" isn't itself a staleness signal here); drop `already_covered` or final < 0.3; `story_count = max(3, round(target_minutes / 1.2))`; per-topic cap = `ceil(story_count / 2)`; one focus-tagged story reserved into position 0 regardless of score (still subject to the 0.3 floor and the already-covered filter — a "reserved slot," not an exemption from relevance); same-event collapsing stays cut per D-22 (simple top-N-per-topic, deduped by article_id across topics so the same article is never selected twice under two different topic tags). Word budget = `target_minutes × 150` words, ±15%, one retry with the validator's own error strings appended to the prompt. TTS chunk size 1,800 characters (under ElevenLabs' documented ≤2,000-character limit, with headroom), packed by whole section first, split at turn boundaries only when a single section exceeds it.

## D-26 — Real .env already had ELEVENLABS_OUTPUT_FORMAT=pcm_44100; a raw-PCM decode bug this caught (2026-09-24, phase 03)
Context: `.env.example` documents `mp3_44100_128` as the default; the project's actual `.env` (set up during phase 00, consistent with ARCHITECTURE §5.6's "Request PCM per chunk and encode MP3 once at the end to avoid double lossy encoding") is actually configured to `pcm_44100`. No fake-provider test caught this — `FakeTTS` always emits a proper self-describing WAV container regardless of the configured format — only the real acceptance run against episode 1 hit it: `assemble.py`'s first version called `pydub.AudioSegment.from_file()` on the `.pcm` chunk files, which failed with a bare `'sample_width'` error, because raw PCM has no header for pydub to sniff a format from.
Decision: `assemble.py` now decodes a `.pcm`-extension chunk explicitly as 16-bit signed little-endian, 44100 Hz, **mono** (`AudioSegment(data=..., sample_width=2, frame_rate=44100, channels=1)`); mp3/wav chunks still go through the normal `from_file`. Mono (vs. stereo) was confirmed empirically, not from ElevenLabs docs: dividing episode 1's five real `.pcm` chunk file sizes by `44100 Hz × 2 bytes` gives a combined ~426s, matching the ~973-word script's expected spoken length at normal pace; the stereo divisor would imply ~213s, half the plausible speaking time for that much text. `ffprobe` on the final assembled mp3 then confirmed `channels=1` directly.
Alternatives: switching `ELEVENLABS_OUTPUT_FORMAT` back to `mp3_44100_128` to sidestep the raw-PCM decode entirely — rejected once the mono assumption was verified live against real audio; PCM is both the architecture's stated preference and, correctly decoded, avoids the double lossy re-encode an mp3-per-chunk pipeline would cost.
Consequences: if a future ElevenLabs plan/voice ever returns something other than mono for `pcm_44100`, this will produce audio at the wrong pitch/speed rather than a clean error — worth a quick listen-check (already part of this phase's acceptance) after any voice or model change, not just a green pipeline run. Locked in with `tests/test_assemble.py`.

## D-29 — Classifier eval (phase 04 Part B): dedicated eval user, CSV labeling, notebook instead of `run_eval.py`/`label.py` (2026-09-24, phase 04, planning)
Context: `docs/phases/04-quality.md` Part B originally specified three scripts: `build_set.py` (~60 candidates from real episodes), `label.py` (terminal labeler writing `labels.jsonl`), and `run_eval.py --classifiers ...` (metrics, then `eval/results/`). The question the eval answers is whether `gpt-6-sol` (about 20x the price of `gpt-6-luna` in `pricing.py`) or Jev earns its cost over Luna, the current default, on the highest-volume LLM call in the pipeline: one classifier call per `(article, topic)` candidate. The classifier returns two independent axes that `rank.py` multiplies (D-25). `relevance` re-checks whether a candidate that Exa's recall-oriented search returned for a topic really meets that topic's description, include and exclude lists. `newsworthy` is about content type: a real event rather than PR, a listicle or an evergreen explainer. A model can fail on one axis without failing on the other, so each gets its own label and its own metric.
Decision (four changes to the phase doc, reviewed before implementation):
1. **Eval set from a dedicated eval user with 5 diverse topics, not the demo user's leftovers.** The demo user's 4 topics were the ones the classifier prompt was informally checked against while it was being built, so reusing them would not test generalization. Build a separate eval user and give it 5 deliberately different topics that vary in ambiguity (e.g. a narrow one like space launches and a fuzzy one like personal finance). Create the profile through the real profile-extraction path (`cli profile --answers`), so topic descriptions and include/exclude lists look like real ones. Then run the real planner and fetch once (`--stop-after fetching`, so no classification has run yet). `build_set.py` samples a per-topic cap of about 12 from that episode's `article_scores` rows to get a balanced set of about 60. A separate user, rather than extending the demo user's profile, keeps `sample.mp3`'s profile, recent headlines and scheduled episodes untouched.
2. **Labeling in a CSV opened in Excel, replacing `label.py`.** `build_set.py` writes `eval/articles.csv` with `encoding="utf-8-sig"`, because Windows Excel misreads UTF-8 without a BOM. Each row is one `(article_id, fetched_topic)` pair, matching D-21's row granularity and the fact that production only scores an article against the topic that fetched it (D-23). The human fills in `label_relevant` (y/n: does it really belong to `fetched_topic`), `label_newsworthy` (y/n), and optionally `label_actual_topic` (which topic it is really about, or 0). The optional column carries no metric; it records query-planner drift across topics. The notebook joins labels back on `(article_id, fetched_topic)`, never on row position, so an accidental partial sort in Excel cannot misalign ground truth.
3. **One notebook, `eval/classifier_eval.ipynb`, replacing `run_eval.py`.** It loads the labeled CSV and builds transient `Article` objects from it (no DB writes). It calls the production adapter classes directly (`LLMClassifier` over the OpenAI LLM adapter for each model, and `JevClassifier` if `TYPESAFE_API_KEY` is set), so what gets measured is exactly what `rank.py` runs. It computes the metrics, plots the trade-offs for `solution.md`, and its last cells write `eval/results/<date>.json` and `eval/results/latest.md`. Metric computation and plots then live in one place instead of a script plus a separate exploration notebook.
4. **Metrics are fixed before looking at results.** Relevance: accuracy, precision and recall against `label_relevant` at a threshold of 0.5, plus ROC-AUC, which does not depend on a threshold. Newsworthy: precision and recall at 0.5, plus ROC-AUC. Also p50/p95 latency and cost per 100 articles, both from the adapter's `Usage`. Selection agreement is computed by feeding each classifier's scores through the production `rank.select_stories` (with `target_minutes=10`, 8 stories) and comparing the selected sets, instead of reimplementing top-N. The rule for picking the default: Luna stays the default unless selection agreement with Sol is low and Sol's gain on the axis where they differ is material. A per-field accuracy gap that never changes which stories get scripted does not justify about 20x the cost.
Rule deviations this entails, accepted deliberately:
- CLAUDE.md says "real calls happen only through the CLI or the running app". The notebook is a third entry point that makes real calls. It is a manual, one-off analysis artifact, not pipeline code, and never runs under pytest.
- It bypasses the runner, so no `pipeline_steps` rows are written and `DAILY_SPEND_CAP_USD` is not checked automatically. The notebook sums `Usage.cost_usd` itself and prints the total. The expected spend is small: about $0.11 for 60 Sol calls, under $0.01 for Luna, and about $0.08 of Exa for the eval user's fetch, by D-21's rates.
- Classifier outputs are cached to `eval/results/scores_<classifier>.jsonl` and reused on re-run, so "Restart & Run All" does not spend money again and nondeterministic LLM scores do not shift between runs. This follows the reuse-persisted-state-over-new-paid-calls working rule.
Alternatives: (a) the original `label.py` + `run_eval.py`, which is more consistent with the repo's CLI-only style but adds a terminal loop for a 60-row judgment task, and exploration and plots would need a second artifact anyway; (b) reusing the demo user's existing candidates, which costs nothing extra but gives narrow, already-seen topics and an unbalanced per-topic mix (8-20 per topic, D-21); (c) 5 hand-written `Topic` objects with a bespoke Exa fetch script, which bypasses the real profile-extraction and planner path, so it would not measure what production sees.
Consequences: `jupyter`/`ipykernel` get added with `uv add --dev` in `backend/`. The notebook is run from the repo root with `uv run --project backend jupyter lab`, per D-11. `app` is importable there because `backend` is an installed package (`uv_build`, module `app`). Notebook outputs stay committed as visible evidence for `solution.md`, and results are only trusted after a clean "Restart & Run All". Ruff lints `.ipynb`, so the phase's lint-clean check covers the notebook. Seeding needs a small extension so the eval user can be created; `seed-users` currently only creates the admin and demo users. Metric code lives in the notebook, not under pytest, so one cell checks each metric function against a hand-computed toy example before it touches real scores. The dashboard (phase 07) reads the JSON results file; no `classifier_eval_runs` table is added.

## D-30 — Grounding check writes its own `pipeline_steps` row directly, not through the runner (2026-09-24, phase 04)

## D-32 — Architectural terminal logging for the CLI and API, stdlib only (2026-09-24, cross-cutting dev experience)
Context: local/dev runs of the CLI produced no visible progress at all -- `app/main.py` called `logging.basicConfig(...)` for the API, but `app/cli.py` never configured logging, so every `logger.info`/`logger.warning` call already present in the pipeline stage modules (`runner.py`, `planner.py`, `fetch.py`, etc., per CLAUDE.md's "one line per stage") was silently dropped by Python's default "no handler" behavior. This is a cross-cutting dev-experience gap, not part of any phase doc, done alongside another session's phase 04 work in a separate worktree (`.claude/worktrees/logging`, branch `feat/logging`) to avoid colliding with its uncommitted changes to `config.py`/`.env.example`/`pricing.py`.
Decision: one new module, `app/logging_setup.py`, with a single `configure_logging(level)` function that both `app/cli.py` (via a `@cli.callback()` that also logs `cli: <command-name>`, never arguments, since `--answers`/`--focus`/emails could otherwise leak into logs) and `app/main.py` (via a FastAPI `lifespan` that logs `API started`) call on startup. It attaches one `StreamHandler` to the root logger (format `%(asctime)s - %(levelname)s - %(name)s: %(message)s`, `%H:%M:%S`), is idempotent (checks for its own handler by a marker attribute instead of `basicConfig(force=True)`, which would rip out pytest's `caplog` handler), and turns noisy third-party loggers (`httpx`, `openai`, `elevenlabs`, `sqlalchemy.engine`, ...) down to WARNING so the architectural lines stand out. A new `LOG_LEVEL` setting (default `INFO`) controls verbosity. The handler is a `_LiveStderrHandler` subclass that resolves `sys.stderr` dynamically via a property on every write, rather than a plain `StreamHandler(sys.stderr)`: Typer's `CliRunner` (used throughout `test_cli.py`) swaps `sys.stderr` in and out and closes the old one around each `invoke()`, so a handler bound to the stream from the first CLI invocation in a test crashed with "I/O operation on closed file" on the second. Existing per-stage summary lines in the stage modules were left alone; new lines added only at the architectural level the user asked for: `runner.run_episode` now logs pipeline start, `-> entering stage X` before each stage, and episode-ready/stopped-after -- and its two existing lines that were previously misleveled as INFO were promoted: stage failure to ERROR, the daily-spend-cap stop to WARNING. `cli.py` gained INFO lines for user creation, episode creation and profile extraction. No logging was added inside the adapters (`app/adapters/`) -- per-provider-request logs are too granular for this "architectural, not exhaustive" goal and can be added at DEBUG later if needed.
Alternatives: a logging library (structlog, loguru) for structured/colored output -- rejected, stdlib is sufficient for terminal-only local/dev logging and adding a dependency isn't warranted (CLAUDE.md's "no premature abstractions" spirit). Also writing to a rotating file under `data/logs/` -- rejected for now; `pipeline_steps` rows are already the durable record of what happened, and the ask was specifically about the terminal.
Consequences: `MAX_TTS_CHARS_PER_EPISODE`-style guardrail failures and stage failures are now visually distinct (ERROR/WARNING vs INFO) on the terminal, matching the user's example (`time - error: grounding phase generated an invalid file`) -- verified live: a `--minutes 1` fake-provider `generate` run correctly logged an ERROR line when the fake script's word count didn't fit the 1-minute budget. `backend/tests/test_logging_setup.py` covers idempotency and the noisy-logger levels; `test_pipeline_runner.py` gained a `caplog`-based test asserting the stage-entry INFO line and the failure ERROR line. This branch (`feat/logging`) is based on local `main` at 6fe4f2b (not `origin/main`, which is several commits behind and predates phases 01-04 entirely -- worth fixing separately, since the worktree helper's default "fresh" base ref silently produced an empty-`backend/` checkout here). Full `uv run pytest -q` shows 3 pre-existing failures unrelated to this change: `ffmpeg` is not on this machine's `PATH`, so the `assembling` stage fails in any test that runs the pipeline all the way through (`test_cli.py::test_new_episode_and_run`, `test_pipeline_runner.py::test_happy_path_reaches_ready` and `::test_resume_from_failed_stage`); everything else (66 tests) passes, and `ruff check`/`ruff format --check` are clean.

## D-33 — JWT auth: HS256, 12h, no refresh; cross-user access is 403 not 404 (2026-09-25, phase 05)
Context: `docs/phases/05-api-scheduler.md` asks for `POST /auth/login` issuing a JWT and `current_user`/`admin_user` dependencies, without specifying token storage/refresh strategy or what a non-owner hitting another user's episode should see.
Decision: `app/auth.py` issues a single HS256 JWT on login (`sub`=user id, `iat`, `exp` 12h out, signed with `JWT_SECRET`) via `pyjwt` (already the project's JWT library, D-14) -- no refresh token, no revocation list, no rotation. The frontend (phase 06) holds it in memory/localStorage and simply re-prompts login after 12h; there is no session table to check for revocation, so a compromised token is valid until it expires. `current_user` decodes the bearer token and loads the `User` row (401 on missing/invalid/expired token or an unknown `sub`); `admin_user` layers an `is_admin` check (403) on top. Cross-user access to an owned resource (an episode that exists but belongs to someone else) is `require_owner_or_admin()` raising 403, not a 404 that would hide the resource's existence -- deliberately chosen for an internal take-home tool where a clear "not yours" beats a misleading "not found" for debugging, not for a multi-tenant product where resource-existence secrecy matters.
Alternatives: refresh tokens + a session/allowlist table -- rejected as unwarranted complexity for a single-evening take-home API with two seeded human users and no real attacker model; 12h covers a demo/review session without needing a refresh flow. 404 for cross-user access -- rejected per the reasoning above.
Consequences: logging out doesn't invalidate a token early (it just expires naturally); acceptable here, called out in `solution.md` as a known simplification. `CORS_ORIGINS` (new `config.py` setting, comma-separated, default `http://localhost:5173`) gates which frontend origins the browser will allow to call the API at all, independent of the JWT check itself.

## D-34 — Background execution model: a plain daemon thread per run, not a task queue (2026-09-25, phase 05)
Context: `POST /episodes/generate` and `POST /episodes/{id}/retry` must return immediately while the (multi-minute, multi-provider) pipeline runs; ARCHITECTURE §3/§8 already commits this project to a single FastAPI process with no worker pool (D-02).
Decision: `_run_in_background()` in `app/api/routers/episodes.py` is `threading.Thread(target=run_episode, args=(episode_id,), daemon=True).start()` -- not FastAPI's `BackgroundTasks` (which would tie the run's lifetime to that one request/response cycle in a way that reads misleadingly for something users poll for over minutes) and not a queue (Celery/RQ), which D-02 already rejected for the whole project. `run_episode` already opens its own DB session per call (`session_scope()`), so it's safe to invoke from a thread that isn't the request's own.
Alternatives: FastAPI `BackgroundTasks` -- workable, but its lifetime and error-handling story is scoped to the enclosing request handler in a way that obscures that this is really a fire-and-forget background job independent of the HTTP response. A task queue -- rejected, matches D-02.
Consequences (the limits, per the phase doc's own ask): a raw daemon thread has no retry, no dead-letter queue, and no visibility into "how many are running" beyond the per-user in-progress guard (`has_episode_in_progress`); if the process is killed mid-run the episode is simply left in a running status until the next boot's startup recovery (D-36) marks it failed for a manual/automatic retry. Two API processes would still double-run scheduled jobs exactly as ARCHITECTURE §8 already documents for the scheduler itself -- this is the same single-instance assumption, not a new one. Thread count is unbounded (no pool/semaphore): fine for a handful of seeded users, would need a bounded executor before real multi-tenant load.

## D-35 — Per-episode `target_minutes` override; episode creation factored out of the CLI (2026-09-25, phase 05)
Context: `docs/phases/05-api-scheduler.md` wants `POST /episodes/generate` to accept an optional `target_minutes` (3-12) that applies to that one episode only, while scheduled runs (ARCHITECTURE §8) always use the user's saved default -- and both the API and the scheduler need the exact same "resolve window start, resolve target length" logic the CLI's `_create_episode` already had, which duplicating a third time would only drift out of sync.
Decision: `EpisodeGenerateRequest.target_minutes: int | None = Field(ge=3, le=12)` -- FastAPI/Pydantic reject an out-of-range value with a 422 before the handler runs, so no manual bounds check is needed. The resolution logic itself (`target_minutes` override, or the user's saved `preferences.target_minutes`, or 6 if that's somehow missing) moved out of `app/cli.py` into `app/pipeline/episodes.py::create_episode()`, used identically by `new-episode`/`generate` (CLI, `trigger=MANUAL`), `POST /episodes/generate` (API, `trigger=MANUAL`) and `run_scheduled_episode` (scheduler, `trigger=SCHEDULE`, always passing `target_minutes=None` so it can never receive an override). `generate_clicked`'s event payload records `{target_minutes, overridden}` so the dashboard (phase 07) can measure focus-request/override usage per ARCHITECTURE §11 without re-deriving it from the episode row.

Consequences: `app/cli.py`'s `_create_episode` is now a thin "look up the user, delegate" wrapper; any future change to window/length resolution only needs to happen in `app/pipeline/episodes.py`.

## D-36 — Startup recovery threshold (`created_at`, 30 min); Starlette `FileResponse` Range support confirmed, resolving ARCHITECTURE's last `[VERIFY]` (2026-09-25, phase 05)
Context: two small `[VERIFY]`/build-doc items needed resolving before they could ship as written: (1) whether an episode "stuck in a running status" should be measured from when it started or from its last observed activity; (2) ARCHITECTURE §7's long-standing `[VERIFY]` on whether Starlette's `FileResponse` supports HTTP `Range` requests out of the box, or whether `GET /episodes/{id}/audio` needs a hand-rolled ranged response.
Decision: (1) `recover_stuck_episodes()` measures elapsed time from `Episode.created_at`, not from the latest `pipeline_steps` activity -- simpler, and a real episode (even with real TTS) finishes in low single-digit minutes per D-27's acceptance run, so a 30-minute `created_at`-based cutoff has generous headroom without needing to track per-stage liveness. (2) Read `starlette==1.7.0`'s (this project's installed version) `FileResponse` source directly: it already branches on the request's `Range` header and returns a `206 Partial Content` with `Content-Range`/`Accept-Ranges` set -- confirmed live in `backend/tests/api/test_episodes.py::test_generate_list_detail_and_audio_range` (a `Range: bytes=0-99` request against a real assembled episode MP3 returns 206 with `Content-Range: bytes 0-99/<size>`). `GET /episodes/{id}/audio` is therefore a plain `FileResponse(episode.audio_path, media_type="audio/mpeg")` with no custom ranged-response code.
Alternatives: measuring staleness from the latest `pipeline_steps.started_at`/`finished_at` for the episode -- rejected as unneeded precision at a 30-minute grain given real run times are minutes, not tens of minutes. Writing a custom range-parsing `Response` subclass -- rejected once the built-in behavior was confirmed working.
Consequences: ARCHITECTURE.md's data-model note and its top-of-file status line both now point at this decision instead of carrying an open `[VERIFY]`; bumped to v0.8. If a future stage is ever slow enough to legitimately run past 30 minutes end-to-end (unlikely at this project's cost/latency profile), `recover_stuck_episodes` would need to switch to activity-based measurement to avoid a false "interrupted".

## D-37 — Per-stage commits in the runner; core API correctness fixes; frontend nice-to-haves deferred (2026-09-25, phase 05b)
Context: a post-phase-05 review found that `run_episode` did the whole pipeline in one DB transaction (`flush()` per stage, one commit when `session_scope()` exited). Three consequences: (1) a poller saw `pending` until the run ended, so phase 06's stage stepper couldn't work; (2) a crash or restart rolled back every completed stage's output *and* its `pipeline_steps` rows, so real provider spend vanished from the records and `DAILY_SPEND_CAP_USD` undercounted, breaking CLAUDE.md's "each stage persists its output"; (3) an interrupted episode was therefore always still `pending`, so phase 05's recovery wrote `failed_stage="pending"`, which the runner's resume logic rejected (`ValueError`), making every such episode unretryable (one real instance was sitting in the dev DB). The same review found API gaps: retry could start two runners on one episode (status stayed `failed` until the thread began), the in-progress guard was check-then-insert (two concurrent callers both pass), `POST /events` accepted any type, any payload and any episode id (anyone could rate someone else's episode or forge `generate_clicked`), and `PUT /preferences` accepted a free-text `tone` (pasted into the script prompt) and any `voice_id` (which only fails at the voicing stage, after the earlier stages are paid for).
Decision: the runner commits after each successful stage; `_start_index` also accepts a legacy `failed_stage="pending"` (resume from the first stage). A partial unique index `uq_episodes_one_in_progress_per_user` on `episodes(user_id) WHERE status NOT IN ('ready','failed')` (migration `a7c3e2d91f40`, also declared on the model so the tests' `create_all` gets it) makes "one in-progress episode per user" a DB guarantee. `create_episode` raises `EpisodeConflict` on that violation (inside a savepoint, so the caller's session stays usable); the API returns 409, the scheduler logs and skips, the CLI prints a message. `has_episode_in_progress` is gone -- the index is the single mechanism. Retry calls `mark_resuming()`, a conditional `UPDATE ... SET status=<failed_stage> WHERE status='failed'` committed *before* the thread starts: a double click matches zero rows (409), and a resume while another episode runs hits the index (409). `EventCreate.type` is a `Literal` of the four client events, `episode_id` is required and must be the caller's own (403 otherwise), `play_progress` needs `payload.position_s >= 0`, `episode_rated` needs `payload.value` of 1 or -1. `tone` is `Literal["conversational","focused","playful"]`; host `voice_id` must be in `CURATED_VOICES`; host names are 1-40 chars.
Alternatives: keeping the Python pre-check and only adding the index -- rejected as two mechanisms for one rule. Row locks (`SELECT ... FOR UPDATE`) for retry -- works, but the conditional UPDATE is one statement and easier to explain.
Deferred on purpose (frontend conveniences, not correctness; agreed with the user as too much for this step): transcript grouped into sections with per-story sources, `my_rating` on episode detail, `trigger`/`focus_request`/`failed_stage` on list items, `next_run_at` on preferences. Phase 06 can add them when it needs them. (Added in D-40.)
Consequences: an episode's intermediate status is now visible to pollers while it runs. Tests that created two in-progress episodes for one user had to change, which is the point.

## D-38 — What a restart does: recover every orphan, auto-resume once, one catch-up run, an hour of misfire grace (2026-09-25, phase 05b)
Context: jobs live only in APScheduler's in-memory store, and runs are daemon threads in the single API process (D-02, D-34). Four ways a restart or a stall silently lost work: (1) D-36's recovery only touched episodes older than 30 minutes, so a run interrupted 5 minutes in stayed "in progress" and blocked the user's Generate (409) and their cron runs until some later restart; (2) interrupted scheduled episodes just sat failed with nobody there to press Retry; (3) a cron fire time that passed while the process was down was forgotten -- on boot each job is rebuilt and APScheduler computes the *next* fire from now; (4) APScheduler 3.11's default `misfire_grace_time` is 1 second, so a run that fires late while the process is alive (laptop asleep at 08:00, woken at 08:20) is logged as "missed" and skipped.
Decision: (1) at boot, `recover_interrupted_episodes()` marks **every** in-progress episode failed with `error="interrupted"` at the stage it was on (`pending` maps to `planning`), and writes a `pipeline_steps` FAILED row (`provider="system"`, `error="interrupted"`) -- visible on the dashboard and used as a counter. D-36's 30-minute `created_at` threshold is removed: in a single process nothing survives a restart, so age is irrelevant. (2) each recovered episode is auto-resumed from that stage via `mark_resuming()` plus a background thread, for manual and scheduled episodes alike (decided with the user), but only if it has been interrupted at most once, so an episode that itself kills the process can't crash-loop. The daily spend cap still applies. Episodes paused deliberately with the CLI's `--stop-after` (the runner now writes `error="stopped after <stage>"`, cleared by the next successful stage) are marked failed so they stop blocking the user, but never auto-resumed -- otherwise starting the API after `--stop-after scripting` would silently pay for TTS. (3) at boot, `catch_up_due()` checks each scheduled user: anchor = the later of their newest scheduled episode's `created_at` and `preferences.updated_at`; if the first cron time strictly after the anchor is already past, the job is registered with `next_run_time=now`. This is a yes/no, not a count: exactly one catch-up run however long the outage (down Monday and Tuesday on a daily 08:00 schedule, back Wednesday 10:00 -> one episode, then Thursday 08:00 as usual), because `resolve_window_start()` starts the news window at the last ready episode, so one episode covers the whole gap and per-slot runs would only add near-empty duplicates. No age cap on catch-up (decided with the user). (4) `BackgroundScheduler(job_defaults={"misfire_grace_time": 3600})`: a run up to an hour late still fires, once (`coalesce` and `max_instances=1` are already APScheduler defaults). Lifespan order: recover -> auto-resume (each resume committed before its thread starts) -> register jobs with catch-up -> start, so a catch-up for a user whose episode was just resumed hits the in-progress index and skips.
Alternatives: APScheduler's persistent `SQLAlchemyJobStore`, which would make misfire grace work across restarts natively -- rejected: a second, pickled copy of each schedule in its own table that can drift from `preferences.schedule_cron`, and harder to explain than a few lines derived from our own tables. Draining in-flight runs on graceful shutdown -- rejected: the runner's open session would overwrite whatever shutdown wrote. A periodic in-process watchdog for threads that hang while the process is alive -- not built (cut first); runs take minutes and provider calls have their own timeouts.
Consequences / accepted limits: a restart just before the next regular fire (07:50 for 08:00) catches up immediately, and the 08:00 run then either finds the catch-up still running (skipped by the index) or produces a thin episode. A CLI `generate` *actively running* while the API boots shares the DB and is treated as interrupted (dev-only). Two API instances would still double-run jobs (ARCHITECTURE §8, unchanged). Verified live on fakes against the test DB: uvicorn hard-killed (`taskkill /F`) during `assembling` kept all seven earlier `pipeline_steps` rows; the restart logged the recovery, wrote the `system`/`interrupted` row, resumed at `assembling` only and reached `ready`. With a `*/2` schedule whose last fire passed during downtime, the restart logged "catch-up run now" and produced exactly one `schedule` episode, which reached `ready`.

## D-39 — Fetch stage's `provider` now comes from the search adapter, not a hardcoded literal (2026-09-25, phase 05b)
Context: D-37 noted, as outside that step's scope, that `fetch.py`'s two `Usage(provider="exa", ...)` returns (no planned queries; the normal summary) were hardcoded regardless of which search adapter actually ran. `runner.py` writes `pipeline_steps.provider` straight from that `Usage`, so a `--search fake` or test run of the fetch stage recorded `provider="exa"` even though no real Exa call happened -- wrong data on the one row (`units_in`/`cost_usd` per CLAUDE.md's "Providers and cost") meant to show which provider actually served a stage.

Consequences: the `provider` attribute is now part of the `SearchSource` protocol surface, so any future search adapter must declare it. D-37's "noted, not fixed" line is removed since this closes it.

## D-40 — API bridge for the phase 06 frontend: media tokens, story-shaped transcript, clearable rating, forced-failure switch (2026-09-26, phase 05c)
Context: phase 06 builds the SPA against the phase 05 API. Reading its spec against the API found gaps. (1) The player is a native `<audio src>`, which can't send `Authorization: Bearer`, so `GET /episodes/{id}/audio` and the voice previews would 401 in the browser. (2) The episode page shows "story headings and source links under each story", but the API returned a flat transcript and a separate sources list. (3) 👍/👎 had no way to show the current rating or undo it. (4) D-37's deferred conveniences (`trigger`/`focus_request`/`failed_stage` on list items, `next_run_at`, `my_rating`). (5) The spec's slider estimate ("~6 min · ~5 stories") and the "empty profile → settings" redirect. (6) The acceptance walkthrough says "retry a forced failure" on fakes, but a fake run couldn't be made to fail. A seventh gap turned up while testing: the fake LLM's script was a fixed 608 words, which only fits the ±15% budget for ~4-minute episodes, so every default 6-minute fake run failed at scripting. That broke 10 existing tests and would have broken the walkthrough.
Decision: (1) `create_media_token(kind, ref)` in `app/auth.py` is a 1-hour HS256 JWT `{media, ref, exp}` with **no `sub`**, so it can never pass `current_user` (which now also returns 401 instead of a KeyError on a token without `sub`). Episode detail returns `audio_url=/episodes/{id}/audio?t=<token scoped to that episode>`. The audio endpoint checks only that token, because the owner-or-admin check already happened when detail handed it out. Voice previews work the same way (decided with the user: kept private rather than public, so they aren't an open download), with `GET /voices` returning tokenised `preview_url`s. (2) `EpisodeDetail.sections` replaces `transcript` + `sources`. Each section is `{kind, story_id, heading, topic, turns, sources}`: `heading` is the story's first source title, and `topic` is that article's best `article_scores.topic` for the episode. (3) `episode_rated` accepts `value: 0` meaning "cleared" (decided with the user). `my_rating` is the caller's latest rating event, with 0 read as null, so events stay append-only. (4) `EpisodeListItem` gets `failed_stage`, `error`, `trigger` and `focus_request`, and detail gets `trigger` and `focus_request`. `PreferencesOut.next_run_at` is computed from the saved cron with APScheduler's `CronTrigger` rather than read from the live scheduler, so it doesn't depend on whether the scheduler thread is running. (5) `GET /preferences/length-options` serves `rank.story_count_for` for 3–12 minutes, so the frontend doesn't keep a drifting copy of the formula. `MeResponse.has_profile` (at least one saved topic) lets the frontend redirect right after login. (6) `FAKE_FAIL_ONCE_AT=<stage>` (config + `.env.example`): the runner raises `forced failure (FAKE_FAIL_ONCE_AT)` at that stage if the episode has no earlier FAILED step there, and **only when TTS is fake**, so it can never throw away a paid run. Retry then succeeds through the normal failure/resume path. (7) `FakeLLM` sizes its story turns from the "about N words" target the script prompt already carries, so fake scripts fit the budget at any length and story count. Because fake runs now go all the way through fake TTS and ffmpeg (about 10 s for a 6-minute episode), the test fixtures' default length went from 6 to 3 minutes. The full suite runs in about 2 min 15 s.
Alternatives: passing the login JWT as `?access_token=` -- rejected, because the 12h full-account token would end up in URLs and server logs. Fetching audio as a blob in the frontend -- rejected, because it loses streaming and Range seeking. A signed URL for the preview endpoint only, with previews otherwise public -- rejected by the user. Storing the rating as a column or a separate table -- rejected, because the events table is already the rating record the phase 07 metrics read. A test-only monkeypatch for forced failure -- rejected, since the walkthrough is a manual run against the real API process.
Consequences: an `audio_url` stops working an hour after the detail response, so the frontend should refetch detail before replaying an old page (TanStack Query's refetch-on-focus mostly covers this). A leaked media URL exposes one file for at most an hour. The `transcript`/`sources` fields are gone from the API contract; no client used them yet. Still failing and out of scope: 5 tests in `test_jev_classifier.py`/`test_fallback_classifier.py`, which came in with the `jev experimentation` merge and reference settings/attributes that don't exist on `main` (`model_jev`, `ai_gateway_api_key`, `Usage.fallback_count`).
